## 这些文档分别在讲什么

### 1) `code.prompt.md`：通用编码执行框架

核心是“实现需求后，必须进入可重复的质量闭环”：

1. 实现需求。
2. 编译并修复编译问题。
3. 运行单测并修复失败。
4. 再跑一轮编译 + 测试，确认回归无问题。

它强调的是**完整开发循环**，适合从自然语言直接落地成代码任务。

### 2) `4-execution.prompt.md`：按执行文档落地改动

核心是“以 `Copilot_Execution.md` 为单一执行事实源”：

- 按 `# EXECUTION PLAN` 落地改动。
- 支持“无标题消息”执行既有计划，或“带 `# Update`”时追加变更。
- 每步可打 `[DONE]`，支持可恢复执行。
- 只要求“编译通过”，**明确不跑单测**（把验证留给后续阶段）。
- 对修复动作要求写原因、策略、预期效果，并记录到 `# FIXING ATTEMPTS`。

它更像“**受控实施阶段**”，强调执行过程可追踪。

### 3) `5-verifying.prompt.md`：验证与回归关闭环

核心是“在不偏离用户最新改动的前提下完成验证”：

- 先比对 `Copilot_Execution.md` 与源码，若发现用户手改，必须尊重并记录。
- 进行编译验证。
- 进行单测验证。
- 编译/测试失败时，迭代修复并持续记录尝试。
- 通过后形成“已验证”状态（文档中要求 `# !!!VERIFIED!!!` 标记）。

它是“**质量闸门阶段**”，目标是把执行结果变成可交付结果。

## 三者组合起来的协议流

可以概括为：

- `code.prompt`：端到端默认流程（实现→编译→测试→复查）。
- `execution.prompt`：把“怎么改”流程化、文档化、可恢复化。
- `verifying.prompt`：把“改完是否可靠”流程化、证据化。

即：**开发动作标准化 + 过程记录标准化 + 质量验证标准化**。

## 可以学习到的技巧

### 技巧 1：把“请求”映射成固定状态机

将自然语言拆成固定阶段（实现、编译、测试、复查），能显著降低漏步骤风险。

### 技巧 2：区分“执行阶段”和“验证阶段”

`execution` 不做测试，`verifying` 专注测试，有助于角色分离，避免上下文混乱。

### 技巧 3：把文档作为执行日志，而不只是说明书

通过 `# FIXING ATTEMPTS` 记录“为什么错、怎么改、为什么有效”，能够沉淀可追溯决策链。

### 技巧 4：要求“最小范围修复”

只修复自己引入的 warning，不顺带清理其他问题，能控制变更面、减少回归风险。

### 技巧 5：强调可恢复执行

步骤打 `[DONE]` 是一种轻量 checkpoint 机制，适合长任务和中断恢复。

### 技巧 6：先尊重用户改动，再谈一致性

当文档与代码不一致，优先尊重用户的最新代码，并记录差异，而不是回滚用户改动。

### 技巧 7：故障定位分层

先断言/日志，再调试器；先低成本验证路径，再高成本单步调试，效率更高。

### 技巧 8：强制回归复查

“再跑一轮”是关键，它防止“修好 A、破坏 B”的隐性回归。

## 对团队流程的启发

- 可以把这套协议沉淀为 PR 模板或 CI gate checklist。
- 可以把 `Fixing Attempt` 结构直接用于缺陷复盘模板。
- 可以将“执行/验证分离”映射到不同角色或不同流水线阶段。
