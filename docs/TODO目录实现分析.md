# TODO 目录实现分析（结合当前仓库）

## 1. 目录角色总览

`ToDo` 目录在这个项目里并不是“零散备忘录”，而是一个**轻量级项目管理系统**，由多个文件协同实现：

- 版本路线图：`1.3.1.0.md`、`1.3.2.0.md`、`1.4.0.0.md`、`1.5.0.0.md`、`1.6.0.0.md`
- 问题池：`KnownIssues.md`
- 创意池：`Unplanned.md`
- 自动化校验脚本：`CheckLinks.1.6.0.0.ps1`

这说明它的设计目标是：
1. 用版本文件承载“当期可执行任务”；
2. 用 `KnownIssues.md` 承载“明确缺陷与风险”；
3. 用 `Unplanned.md` 承载“未来想法与暂不排期需求”；
4. 用脚本做最小自动化质量保障（当前是链接可用性校验）。

---

## 2. 核心逻辑是如何实现的

## 2.1 版本维度的任务分层

以 `1.6.0.0.md` 为代表，一个版本文件内部固定分为：

- `Milestone`：目标（做什么）
- `Instructions`：执行规约（怎么做）
- `Plan`：可勾选研究/实现条目（做到哪一步）
- `Details`：条目对应的沉淀内容（为什么这样做）

这四层形成了“目标 -> 过程 -> 结果”的闭环。

## 2.2 Plan 的状态机（[ ] -> [+] -> [*]）

`1.6.0.0.md` 里把执行步骤写得非常明确，本质是一个三态状态机：

- `- [ ]`：未开始
- `- [+]`：进行中
- `- [*]`：已完成

并且规定了处理顺序：

1. 永远取第一个未完成项；
2. 先改成 `- [+]` 并保存；
3. 在 `Details` 建同名 `###` 小节并填写内容；
4. 完成后改为 `- [*]`。

这就是一个可追踪、可恢复的顺序执行机制。即使中断，也能从 `- [+]` 精确续跑。

## 2.3 “研究文档驱动开发”

`1.6.0.0.md` 的 `Instructions` 不是要求立刻改 C++ 代码，而是先把“外部规范（MSDN / Learn）+ 接口体系 + 设计映射”整理成可执行知识。

即：

- 先把标准弄清楚；
- 再把控件模型和平台接口模型对齐；
- 最后再进入编码。

这个顺序能减少后期返工，尤其适合 UI Automation 这种标准驱动功能。

## 2.4 自动化校验逻辑（脚本层）

`CheckLinks.1.6.0.0.ps1` 做的事情可以概括为：

1. 读取目标 Markdown；
2. 正则提取所有 URL；
3. 优先 `HEAD`，失败则退化到 `GET`；
4. 记录状态码、重定向后的最终地址、错误信息；
5. 有坏链就 `exit 1`。

这虽然简单，但非常关键：

- 避免 `Details` 里长期沉淀失效链接；
- 保证计划文档可持续维护；
- 可以接入 CI（通过返回码判断是否通过）。

## 3. 完整案例（一步一步推理演示）

下面用 `1.6.0.0.md` 中 “How WM_GETOBJECT works” 这个条目，演示这套机制如何落地。

## 3.1 输入（要做什么）

`Plan` 中存在条目：`How WM_GETOBJECT works`。

## 3.2 步骤 1：占位并加锁

把该条目从 `- [ ]` 改为 `- [+]`。

推理：这一步相当于“声明我在做”，防止多人并行时重复研究，也能在中断后定位到未完成工作。

## 3.3 步骤 2：创建对应详情章节

在 `Details` 新增：`### How WM_GETOBJECT works`。

推理：`Plan` 是索引，`Details` 是正文。没有这个映射，后续就无法从计划项直接跳到结论。

## 3.4 步骤 3：补全证据链（外部规范）

该章节下补齐核心链接：

- WM_GETOBJECT 消息说明
- Handling WM_GETOBJECT
- `UiaReturnRawElementProvider`

推理：先建立“规范证据链”，才能判断后续接口实现是“必须”还是“可选”。

## 3.5 步骤 4：抽取实现要点

将规范转译为工程语言，例如：

- 何时返回 UIA provider；
- `dwObjId == UiaRootObjectId` 的语义；
- 返回值应如何由 `UiaReturnRawElementProvider` 形成。

推理：这一层把“文档知识”变成“可编码决策”。

## 3.6 步骤 5：回写完成状态

确认 `Details` 可指导编码后，把 `Plan` 条目改为 `- [*]`。

推理：`[*]` 不是“写了点东西”，而是“达到可执行标准”。

## 3.7 步骤 6：脚本校验可维护性

运行 `CheckLinks.1.6.0.0.ps1`，检查该章节链接是否可访问。

推理：确保知识资产长期有效，避免半年后文档无法作为实施依据。

## 5. 结论

当前项目 `ToDo` 目录的实现不是“写清单”，而是：

- 用版本文件构建可执行任务流；
- 用 `Plan` 三态构建可恢复状态机；
- 用 `Details` 进行知识沉淀和实现前置设计；
- 用脚本进行最小自动化质量约束。

这套机制非常适合复杂特性（如 UI Automation）：先把标准和映射吃透，再进入代码实现，能显著降低反复返工概率。

## 6. 你问的这几类文件“分别都记录什么”（详细版）

你提到的四类我按“用途、内容结构、怎么用”分别展开。

### 6.1 版本路线图：`1.3.1.0.md` ~ `1.6.0.0.md`

这批文件是**按版本切片的执行账本**，每个版本记录当期目标、已完成事项和后续任务，核心作用是把“长期演进”拆成“可落地里程碑”。

- `1.3.1.0.md`
  - 记录了“已修复问题（Fixed Bugs）”“已完成事项（Finished）”和下一步 Milestone。
  - 同时有一段 `Copilot` 使用规范沉淀，偏流程工具化。适合回溯“这个小版本到底交付了什么”。
- `1.3.2.0.md`
  - 增加 `Known Issues`（该版本语境下的已知问题）+ 更细的 Milestone 列表。
  - 内容显著偏向“远程协议、测试覆盖、流程自动化”三个方向。
- `1.4.0.0.md`
  - 聚焦功能扩展：`RawElement`、`DocumentElement`、SyncObj、教程等。
  - 偏“能力建设型版本规划”。
- `1.5.0.0.md`
  - 聚焦跨平台、UIA、远程协议、参数系统等中期工程方向。
  - 同时出现“Release 示例工程”和测试搬运策略，说明开始关注对外可用性与发布工程。
- `1.6.0.0.md`
  - 明确采用 `Milestone / Instructions / Plan / Details` 结构。
  - 该版本不是简单列任务，而是提供“研究步骤 + 状态机 + 知识沉淀”的完整执行模型，尤其用于 UI Automation 的规范化推进。

**怎么用**：
1. 先看最新版本（当前是 1.6.0.0）确定“主航道”；
2. 再回看 1.3.x ~ 1.5.x，识别“历史决策和未完全收敛事项”；
3. 执行时优先跟随最新版本中的 `Plan/Details` 机制。

### 6.2 问题池：`KnownIssues.md`

`KnownIssues.md` 是**跨版本集中缺陷池**，用于收纳“不一定本版本修，但必须被记住”的问题。

其特点：

- 按主题分组：例如 `Vlpp`、`Remote Protocol`、`Unit Test`、`Depriorized`。
- 既有明确 bug，也有“测试脆弱点、架构债务、可观测异常”。
- 含“可暂缓（Depriorized）”区，避免核心列表被低优先级事项淹没。

**怎么用**：
- 做计划时从这里拉取“高频/高风险项”进当前版本 Milestone；
- 做回归测试时按 `Unit Test` 子项生成检查清单；
- 评估稳定性时，把它当风险雷达，而不是普通 TODO 列表。

### 6.3 创意池：`Unplanned.md`

`Unplanned.md` 是**未来能力储备池**，记录的是“有价值但暂不排期”的设想，不要求短期可交付。

其特点：

- 范围非常广：从 XML 资源语法扩展、拖拽框架、图形能力到多平台与多语言移植。
- 更强调“方向”和“可能性”，而不是实施细节与截止时间。
- 本质是产品/架构方向备忘，不是迭代执行清单。

**怎么用**：
- 做 Roadmap 评审时，从这里挑可转化为 Milestone 的条目；
- 需求讨论时把“想法”先沉淀到这里，避免污染当前迭代；
- 当某技术前提成熟后，再迁移到对应版本文件实施。

### 6.4 自动化校验脚本：`CheckLinks.1.6.0.0.ps1`

该脚本是**文档质量守门员**，专门针对 `1.6.0.0.md` 的外链质量做自动检查。

它具体记录/处理的信息包括：

- 输入参数：目标文件路径、超时秒数、最大重定向次数；
- 从文档中抽取出的 URL 列表（去重后）；
- 每个 URL 的状态码、最终跳转地址、错误信息；
- 总坏链数量（`BAD_COUNT`），并通过进程退出码反馈结果。

这意味着它不仅是“检查脚本”，还是“文档健康报告生成器”：

- 你能看到哪些链接 200/301；
- 哪些链接失败；
- 最终是否应判定为 CI 失败（`exit 1`）。

**怎么用**：
- 在更新 `1.6.0.0.md` 的 `Details` 后运行一次；
- 若 `BAD_COUNT > 0`，先修链接再提交；
- 可以直接挂到流水线中作为文档门禁。

## 7. 这个 ToDo 是人工写的，还是 AI Agent 自己迭代的？

结论先说：**从仓库证据看，主体是人工（仓库维护者）持续编写与迭代；AI 更像被“指挥去执行/补全”的对象，不是主作者。**

### 7.1 证据 1：Git 提交作者与历史连续性

`ToDo/1.6.0.0.md` 近几次更新都来自同一作者 `vczh`，并且是短时间连续多次人工迭代（补计划、补细节、补脚本关联），而不是一次性机器批量生成。

- 例如：`d72512e`、`49a6599`、`45d62df`、`af30420`、`45922d7` 等提交，作者均为 `vczh`。
- `git blame` 也显示 `1.6.0.0.md` 大段关键内容（Instructions / Plan / Details）由这些提交逐步写入。

### 7.2 证据 2：文本内容是“在指导 AI 工作”而不是“AI 自述产物”

`1.6.0.0.md` 的 `Instructions` 明确使用了任务分发口吻：

- “Pick the first incomplete item ...”
- “You can start a sub agent ...”
- “Mark the item ...”

这类写法语义上是“人给执行代理下流程指令”，而不是 AI 自发记录。

### 7.3 证据 3：跨版本长期演进风格一致

从 `1.3.1.0` 到 `1.6.0.0` 能看到长期路线演进：

- 早期更偏功能与 bug 清单；
- 中期开始加入远程协议、跨平台、测试策略；
- 到 1.6 升级为 Plan/Details 的流程化研究机制。

这种“版本间连续演化 + 上下文承接”很像维护者长期管理项目的产物，而非单次 AI 输出。

### 7.4 证据 4：出现“人工管理痕迹”

文件中有大量“优先级、可选项、延期项、命名修订、流程提醒”等管理语句，并混合少量拼写问题（如 `retrive`、`acception`、`protodol`），这更符合人工长期编辑痕迹。

### 7.5 更谨慎的表述（避免绝对化）

基于仓库内部可见证据，我们可以高置信度判断：

- **ToDo 主体由人工维护；**
- **部分内容可能借助 AI 辅助整理或补写；**
- 但“AI 自己独立迭代 ToDo 并作为主导作者”的证据不足。
